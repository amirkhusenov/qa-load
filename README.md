# QA Load Testing

## Описание проекта

Проект содержит сценарий нагрузочного тестирования цепочки из трёх HTTP endpoint, развёрнутых в Mockoon. Нагрузка генерируется Locust, а отдельный скрипт на `psutil` записывает системные метрики операционной системы в CSV.

Проверяемый поток запросов:

1. `GET /api/first` возвращает идентификатор;
2. этот идентификатор передаётся в `GET /api/second?value=<ID>`;
3. после успешного ответа второго endpoint идентификатор помещается в очередь;
4. `GET /api/third?value=<ID>` получает идентификаторы из очереди.

По условию прогона целевая длительность нагрузки — один час. На момент анализа CSV содержал замеры с `2026-09-30 22:49:11` по `2026-10-01 00:06:48` (4 652 строки данных, интервал 77 мин 37 с). Файл продолжает дописываться `monitor.py`, поэтому по одному CSV нельзя точно сопоставить весь мониторинговый интервал с заявленным часовым прогоном Locust.

## Технологии

- **Python** — язык сценариев нагрузки и мониторинга.
- **Locust** — генерация HTTP-нагрузки и сбор результатов запросов.
- **Mockoon** — тестовый HTTP-сервер с тремя endpoint.
- **psutil** — сбор system-level metrics: CPU, память и дисковый I/O всей ОС.
- **CSV** — хранение замеров мониторинга.
- **Git** — указан в технологическом стеке задания для контроля версий. Каталог `.git` в доступной рабочей копии отсутствует.

## Архитектура теста

```text
GET /api/first
      ↓
получение ID
      ↓
GET /api/second?value=<ID>
      ↓
проверка ID и успешный ответ
      ↓
verified_ids (Queue)
      ↓
GET /api/third?value=<ID>
```

`Queue` используется для безопасной передачи ID между разными типами виртуальных пользователей. Второй пользователь добавляет ID в `verified_ids` лишь при HTTP 200 от `/api/second`, а третий пользователь извлекает его с таймаутом и не выполняет запрос, если очередь пуста.

Роли элементов сценария:

- `latest_id` — общая переменная: хранит последний ID, полученный `FirstUser`, для последующего запроса `SecondUser`.
- `verified_ids` — потокобезопасная очередь ID, прошедших второй endpoint.
- `constant_pacing(1)` — стремится поддерживать период выполнения задачи около одной секунды с учётом времени самого запроса. Он не гарантирует строгое количество RPS.
- `fixed_count` — фиксирует число активных пользователей каждого класса: 30 для первого endpoint, 20 для второго, 10 для третьего.

## Настройка Mockoon

В задании для Mockoon описаны следующие маршруты:

| Endpoint | Назначение |
|---|---|
| `GET /api/first` | Возвращает ID для начала цепочки. |
| `GET /api/second?value=<ID>` | Принимает и проверяет ID, полученный на первом шаге. |
| `GET /api/third?value=<ID>` | Принимает ID, успешно обработанный вторым шагом. |

В задании указано, что для endpoint была включена random latency с фактическим диапазоном примерно **0–1500 мс**; это не следует интерпретировать как строго заданный диапазон 500–1500 мс. Конфигурация Mockoon в рабочей папке отсутствует, поэтому этот диапазон не подтверждается локальным конфигурационным файлом.

## Нагрузочный профиль

| Endpoint | Target RPS | Actual RPS |
|---|---:|---:|
| `/api/first` | 30 | 28.2 |
| `/api/second` | 20 | 18.3 |
| `/api/third` | 10 | 9.0 |

Фактический RPS немного ниже целевого. В сценарии используется `constant_pacing(1)`: он регулирует частоту выполнения задач отдельными виртуальными пользователями, но не гарантирует абсолютно точный RPS. Время выполнения задач, включая время HTTP-ответа, может влиять на достигнутую частоту. Конкретные причины отклонения RPS нельзя установить без временного ряда или экспорта Locust.

## Запуск проекта

Ниже приведены команды для Windows PowerShell и Git Bash. Адрес и порт Mockoon в репозитории не зафиксированы, поэтому их нужно указать при запуске Locust в соответствии с запущенной конфигурацией Mockoon.

### Windows PowerShell

```powershell
py -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
python -m pip install psutil
```

Запустите Mockoon с конфигурацией трёх endpoint, затем в отдельных терминалах:

```powershell
python monitor.py
```

```powershell
locust -f locustfile.py --host http://<mockoon-host>:<port>
```

### Git Bash

```bash
python -m venv .venv
source .venv/Scripts/activate
python -m pip install -r requirements.txt
python -m pip install psutil
```

После запуска Mockoon:

```bash
python monitor.py
```

```bash
locust -f locustfile.py --host http://<mockoon-host>:<port>
```

`monitor.py` импортирует `psutil`, однако текущий `requirements.txt` содержит только `locust==2.46.6`. Поэтому `psutil` устанавливается отдельной командой. Это отражает фактическое состояние репозитория; файл зависимостей намеренно не изменялся.

## Конфигурация Locust

`locustfile.py` определяет три независимых класса виртуальных пользователей:

| Класс | Число пользователей | Задача |
|---|---:|---|
| `FirstUser` | 30 | Вызывает `/api/first` и сохраняет поле `id` ответа в `latest_id`. |
| `SecondUser` | 20 | Берёт текущий `latest_id`, вызывает `/api/second` и при статусе 200 добавляет ID в `verified_ids`. |
| `ThirdUser` | 10 | Извлекает ID из `verified_ids` и вызывает `/api/third`. |

Таким образом, значение ID передаётся сначала через `latest_id`, затем через очередь `verified_ids`. Если первый endpoint ещё не вернул ID, второй пользователь завершает текущую задачу без запроса. Если в очереди нет ID, добавленных после HTTP 200 от `/api/second`, в течение двух секунд, аналогично завершается задача третьего пользователя.

## Мониторинг ресурсов

`monitor.py` получает процент CPU с `psutil.cpu_percent(interval=1)`, затем записывает процент занятой памяти и приращения системных счётчиков диска. Поля `disk_read_mb_s` и `disk_write_mb_s` вычисляются как разница байтовых счётчиков, делённая на `1024 ** 2`; код не измеряет фактическую длительность интервала. Поэтому их значения следует трактовать как объём I/O в MiB между соседними замерами, рассчитанный с предположением интервала около секунды, а не как строго измеренную скорость MiB/s. Все значения являются **system-level metrics**: они относятся ко всей операционной системе, а не исключительно к процессу Mockoon.

| Метрика | Среднее | Минимум | Максимум |
|---|---:|---:|---:|
| CPU | 10.11% | 0.40% | 72.90% |
| Использование памяти | 61.29% | 58.10% | 75.70% |
| Disk read (за интервал замера) | 0.340 MiB | 0.000 MiB | 233.257 MiB |
| Disk write (за интервал замера) | 0.266 MiB | 0.000 MiB | 187.805 MiB |

На момент расчёта CSV охватывал 77 мин 37 с, а не ровно один час. Поэтому таблица описывает весь доступный мониторинговый интервал на этот момент, но не позволяет выделить показатели только часового прогона без дополнительных временных границ запуска Locust. При продолжающемся запуске `monitor.py` числа в CSV и в этой таблице будут изменяться.

## Анализ результатов

### Фактические результаты

- Выполнено 197 479 HTTP-запросов к трём endpoint; в данных Locust указано 0 ошибок.
- Полученные 28.2, 18.3 и 9.0 RPS близки к запланированным 30, 20 и 10 RPS.
- Среднее время ответа составило 770.54–774.38 мс для отдельных endpoint; агрегированное значение — 772.75 мс.
- P95 составил 1400–1500 мс, P99 — 1500 мс; единичные запросы достигали 2860 мс.
- На момент расчёта по всему доступному CSV средняя загрузка CPU составила 10.11%, среднее использование памяти — 61.29%.

### Интерпретация

Наблюдаемая нагрузка близка к планируемому распределению по endpoint с небольшим отклонением RPS. Указанный в задании диапазон random latency может объяснять заметный разброс времени ответа, но без файла конфигурации Mockoon причинно связать его с результатами нельзя. Средние значения system-level CPU и памяти существенно ниже своих максимумов; пиковые значения CPU и рассчитанных приращений disk I/O присутствуют в CSV.

### Ограничения теста

- В задании для Mockoon указана random latency примерно 0–1500 мс, а не строго 500–1500 мс; локальный конфигурационный файл Mockoon отсутствует.
- `constant_pacing` не гарантирует строгое число запросов в секунду.
- `psutil` собирает показатели всей операционной системы; их нельзя приписывать только Mockoon.
- `metrics.csv` на момент расчёта охватывал 77 мин 37 с и продолжал изменяться, поэтому файл не подтверждает, что в него попал только заявленный часовой прогон.
- Экспорт отчёта Locust и конфигурация Mockoon не включены в рабочую папку; результаты и настройки из соответствующих разделов опираются на предоставленные данные задания.
- Результаты характеризуют конкретный тестовый прогон и не являются универсальной характеристикой производительности приложения.
